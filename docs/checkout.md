# خرید، آدرس و سفارش

مسیر خرید: `/cart` → `/checkout/address` → `/checkout/place-order` → `/orders/[id]`.

سبد مهمان عمومی و در مرورگر باقی می‌ماند. ورود در اولین قدم checkout الزامی است و پس از ورود کاربر به همان آدرس برمی‌گردد. فرم آدرس شامل استان، شهر، نشانی کامل، کد پستی و شماره تماس است. نام گیرنده از حساب کاربر گرفته می‌شود. در این MVP آخرین آدرس ذخیره‌شده خوانده و همان رکورد ویرایش می‌شود؛ انتخاب چند نشانی هنوز رابط ندارد. ارقام فارسی و عربی به لاتین تبدیل می‌شوند و صفر ابتدای شماره‌ها حفظ می‌شود.

`actions/address.actions.ts` آدرس کاربر جاری را ذخیره می‌کند. `actions/cart.actions.ts` سبد محلی را پس از بررسی SKU، وزن، قیمت و فعال‌بودن محصول در سبد حساب ذخیره می‌کند. شناسه‌های محلی همان slug انتخاب دقیق محصولات هستند و در سرور به شناسهٔ واقعی محصول تبدیل می‌شوند. `actions/order.actions.ts` سفارش و ردیف‌ها را در یک transaction ایجاد می‌کند. هیچ userId، نقش، قیمت یا مجموع ارسالی از کلاینت منبع اعتبار نیست.

صفحهٔ تأیید، قیمت و وضعیت فعال‌بودن Productهای دیتابیس را می‌خواند. hash مشخصات پیشنهاد شامل ردیف‌ها، قیمت‌ها و نشانی است؛ تغییر آن‌ها پیش از کلیک نهایی نیازمند تازه‌کردن صفحه و تأیید دوباره است. ثبت سفارش اطلاعات گیرنده و کالا را snapshot می‌کند؛ ویرایش آدرس یا محصول در آینده سفارش گذشته را تغییر نمی‌دهد.

برای جلوگیری از سفارش تکراری، هر بار آماده‌کردن سبد برای checkout یک `checkoutKey` دارد؛ روی Order یکتا است. ارسال دوبارهٔ همان درخواست، حتی هم‌زمان یا پس از خطای شبکه، همان سفارش قبلی را برمی‌گرداند. نویسندگان آدرس، سبد و سفارش ردیف حساب را در transaction قفل می‌کنند تا تغییرات همان حساب با هم تداخل نکنند. سفارش فقط برای مالک آن قابل مشاهده است. حساب کاربری ۲۰ سفارش اخیر را نمایش می‌دهد.

## محدودهٔ این مرحله

طبق تصمیم کاربر، هزینهٔ ارسال و درگاه پرداخت مرحلهٔ بعد هستند. سفارش با `PENDING` و `UNPAID` ذخیره می‌شود. `shippingFeeFinalized=false` یعنی ارسال هنوز قیمت‌گذاری نشده؛ صفر فیلد shippingFee به معنی ارسال رایگان نیست. مبلغ نمایش‌داده‌شده «جمع فعلی سفارش» است. دکمهٔ پرداخت غیرفعال است و هیچ مبلغی دریافت نمی‌شود.

مدیریت موجودی فعلاً کنار گذاشته شده است: مدل Product ستون `stock` ندارد و برای رفتن به بررسی سفارش یا ثبت آن، شرط تعداد موجودی نداریم. سقف تعداد هر SKU همچنان ۱۰۰ است. قیمت مثبت، SKU معتبر و `isActive=true` همچنان لازم‌اند. سبد محلی پس از سفارش باقی می‌ماند. اتصال درگاه و طراحی مدیریت موجودی کارهای جداگانهٔ آینده‌اند.

فهرست محصولات و انتخاب وزن/رست از `lib/storefront.ts` می‌آید؛ مبنای ثبت سفارش قیمت SKU متناظر در Neon است. محصولات بدون قیمت قابل سفارش نیستند. seed محصولات جدید را غیرفعال ایجاد می‌کند؛ پیش از سفارش، وضعیت فعال آن‌ها باید تنظیم شود. جزئیات در [راهنمای فهرست](catalog.md) آمده است.

## راه‌اندازی و آزمون

```bash
npm run db:generate
npm run db:deploy
npm run db:seed:products
npm run dev
```

بعد از تغییر schema و تولید Prisma Client، سرور توسعه را دوباره اجرا کنید تا singleton قدیمی جایگزین شود. migration اولیهٔ checkout نام `20260908010000_checkout` دارد. migration جدید `20261013000000_remove_product_stock` فقط ستون `stock` و CHECK مربوط به آن را حذف می‌کند؛ رکورد محصولات، قیمت‌ها و سفارش‌ها باقی می‌مانند.

```powershell
npm run test:unit
npm run typecheck
npm run lint
npm run build
$env:CHECKOUT_E2E='1'
npx.cmd playwright test tests/ui/checkout.spec.ts
```

تست واقعی به Neon و یک SKU نمونهٔ فعال و قیمت‌دار نیاز دارد؛ موجودی تعریف نمی‌شود. فقط هویت‌ها، نشانی‌ها، سبدها و سفارش‌های تصادفی خودش را می‌سازد و پاک می‌کند؛ محصولات و حساب‌های seed تغییر نمی‌کنند. ذخیره و بازیابی آدرس، ارقام فارسی، snapshot نشانی، قیمت سرور، رد پیشنهاد پس از تغییر تعداد، درخواست تکراری، ماندگاری سفارش و جلوگیری از مشاهده/ثبت سفارش با حساب دیگر در مرورگر بررسی می‌شوند.
