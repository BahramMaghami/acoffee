# پرداخت زرین‌پال — sandbox

## اصلاح callback و verify

طبق [راهنمای رسمی اتصال](https://www.zarinpal.com/docs/paymentGateway/connectToGateway.html)،
callback با `Status=OK` برای Authority شناخته‌شده، verify را مستقیماً آغاز می‌کند؛
inquiry و تغییر وضعیت `IN_BANK` پیش‌شرط آن نیستند. مبلغ از دیتابیس خوانده می‌شود.
تنها پاسخ معتبر verify با کد ۱۰۰ یا ۱۰۱ و شمارهٔ پیگیری، سفارش را پرداخت‌شده می‌کند.
`NOK` فقط به سفارش برمی‌گردد و وضعیت مالی یا سهمیه را تغییر نمی‌دهد؛ Status مفقود،
تکراری یا نامعتبر رد می‌شود. callback برای تأیید به session وابسته نیست، اما مشاهدهٔ
جزئیات سفارش همچنان نیازمند مالکیت یا نقش مدیر است.

`verificationStartedAt` شروع گردش تأیید را ثبت می‌کند، حتی اگر بررسی دیگری lease
داشته باشد. بررسی بعدی، تأیید شروع‌شده را مستقیماً با verify ادامه می‌دهد؛ در نتیجه
timeout یا callback هم‌زمان باعث انتظار دائمی برای inquiry نمی‌شود. رزرو تخفیف،
مبلغ، محیط، مرچنت، سفارش جایگزین‌شده و قفل ثبت یک‌باره همچنان کنترل می‌شوند.
پاسخ نامشخص پرداخت را موفق نمی‌کند و ظرفیت تخفیف را آزاد نمی‌کند.
این تغییر migration ندارد؛ سوابق پرداخت‌های قدیمی برگشت‌خورده تغییر نمی‌کنند.

## تنظیمات

```dotenv
ZARINPAL_MERCHANT_ID=f58f584a-2d2a-4daa-974a-8259d22ba8e6
ZARINPAL_SANDBOX=true
PAYMENT_BASE_URL=http://localhost:3000
```

این UUID فقط برای sandbox است. آدرس پایه باید origin ثابت بدون path، query یا اطلاعات کاربری باشد. HTTP فقط برای localhost، 127.0.0.1 و ::1 در sandbox پذیرفته می‌شود؛ محیط واقعی HTTPS می‌خواهد. تنظیمات فقط در سرور استفاده می‌شوند و در صورت نقص، ایجاد پرداخت بسته می‌ماند. پس از تغییر env، سرور Next را دوباره اجرا کن. اگر سایت روی پورت دیگری باز است، `PAYMENT_BASE_URL` هم باید همان پورت را داشته باشد.

مرجع‌ها: [درخواست](https://www.zarinpal.com/docs/paymentGateway/request.html)، [sandbox](https://www.zarinpal.com/docs/paymentGateway/sandBox.html)، [مستندات درگاه](https://www.zarinpal.com/docs/). اتصال REST مستقیم است تا `metadata.auto_verify=false`، timeout و اعتبارسنجی پاسخ صریح باشند. کد سفارش sandbox/live مشترک است و فقط مقصد درگاه و شناسهٔ محیط فرق دارند. مبلغ سفارش تومان است؛ مبلغ تلاش پرداخت ریال و ثابت است. حداقل مستند درخواست ۱۰٬۰۰۰ ریال است؛ مبلغ کمتر خودکار افزایش نمی‌یابد. صفر مبلغ فقط با تسویهٔ بدون درگاه نهایی می‌شود.

## فایل‌ها و جریان

| بخش | محل |
| --- | --- |
| تنظیمات، مبالغ و قواعد حذف | `lib/payment-rules.ts` |
| request / inquiry / verify با timeout پانزده‌ثانیه‌ای | `lib/zarinpal.ts` |
| ماشین وضعیت، قفل و ثبت تسویه | `lib/payments.ts` |
| عملیات مالک سفارش و مدیر | `actions/payment.actions.ts` |
| callback مستقل از session | `app/api/payments/zarinpal/callback/route.ts` |
| کنترل‌ها و سابقهٔ مشتری | `app/orders/[id]/payment-*.tsx` |
| ثبت/ابطال دستی مدیر | `app/admin/orders/manual-payment-form.tsx` |
| رزرو و مصرف کد تخفیف | `lib/discount-codes.ts` |
| تطبیق دستی تراکنش‌ها | `scripts/reconcile-payments.ts` |

ثبت سفارش با checkoutKey تکرارپذیر است. مبلغ و اقلام در سرور دوباره خوانده می‌شوند؛ سفارش و رزرو سهمیه یک تراکنش دارند. سپس تلاش پرداخت ساخته و لینک درگاه پس از ذخیرهٔ authority به مرورگر داده می‌شود. مهلت اولیه ۳۰ دقیقه است. ارتباط شبکه خارج از تراکنش دیتابیس انجام می‌شود؛ هر کار شبکه‌ای lease کوتاه دارد و نتیجه تنها با همان lease پذیرفته می‌شود.


در محیط sandbox، سفارش و سابقه علامت آزمایشی دارند و گزارش فروش واقعی آن‌ها را نمی‌شمارد. آمار سهمیهٔ کد تخفیف نیز بر اساس محیط جداست؛ مصرف‌های قدیمی بدون محیط در بخش واقعی شمرده می‌شوند. هزینهٔ ارسال جداگانه دریافت می‌شود و در مبلغ آنلاین صفر، به معنی ارسال رایگان نیست.

## تخفیف، سفارش قدیمی و پرداخت دستی

- پیش‌نمایش کد مصرفی ندارد. هنگام ثبت سفارش، زیر قفل ردیف کد، مصرف‌های قطعی و رزروهای ACTIVE برای سقف N کاربر و M بار شمرده می‌شوند.
- پایان زمان به‌تنهایی رزرو را آزاد نمی‌کند. تراکنش نامشخص یا در بانک ظرفیتش را نگه می‌دارد. شکست قطعی یا سفارشی که هیچ لینک پرداختی نگرفته و مهلتش تمام شده، می‌تواند رزرو را آزاد کند. بررسی پرداخت دیرهنگام تنها با رزرو همچنان معتبر انجام می‌شود.
- تسویه و تبدیل رزرو به مصرف یک تراکنش و یک‌بارمصرف‌اند. تسویهٔ صفر با روش DISCOUNT انجام می‌شود. مصرف‌های تاریخی بدون تغییر باقی می‌مانند.
- سفارش قدیمی/شکست‌خورده باید «بررسی قیمت روز و پرداخت» را طی کند. پس از تأیید جایگزینی سبد، اقلام با قیمت روز نمایش داده می‌شوند و اقلام حذف‌شده/آسیاب ناقص باید اصلاح شوند. ثبت بعدی سفارش جدید با `repricedFromId` است. کد قدیمی منتقل یا سهمیهٔ تاریخی پس داده نمی‌شود.
- مدیر می‌تواند فقط سفارش تازه و واجد شرایط را بدون تلاش فعال/نامشخص با مبلغ ثابت و توضیح اجباری تسویه کند. نام و شناسهٔ مدیر و زمان از سرور ثبت می‌شوند. ابطال فقط برای تسویهٔ MANUAL با دلیل و سابقه است؛ مصرف کد برنمی‌گردد. پرداخت موفق زرین‌پال از پنل ابطال نمی‌شود.
- تغییر تحویل مستقل می‌ماند. حذف سفارش PAID/REFUNDED، دارای تلاش موفق، تلاش فعال یا هر سابقهٔ MANUAL مسدود است. حذف سفارش فاقد این سوابق همچنان تأیید داخل صفحه دارد.

## تطبیق تراکنش‌های معلق

پس از اعمال migration، در sandbox به‌صورت دستی اجرا کن:

```powershell
npm.cmd run payments:reconcile
```

این دستور نوشتنی است: حداکثر ۱۰۰ سفارش بلاتکلیف را با همان منطق callback بررسی می‌کند؛ خروجی فقط آمار است. رزروها را صرفاً به‌خاطر زمان آزاد نکن و وضعیت UNKNOWN را دستی PAID یا FAILED نکن. در صورت تغییر مرچنت، تلاش قبلی باید با تنظیمات مرچنت خودش تعیین تکلیف شود.

پیش از فعال‌سازی واقعی، اجرای دوره‌ای (مثلاً هر ۵ دقیقه) روی سرور، پایش خروجی/خطا، بررسی موارد UNKNOWN و آزمون کامل branch آزمایشی لازم است. اسکریپت در محیط LIVE بدون `--live` اجرا نمی‌شود. در این مرحله cron، پرداخت واقعی و حالت production فعال نشده‌اند.

## Migration و آزمون

`20261108000000_zarinpal_payments` دو جدول تلاش و رزرو، enumها، فیلدهای اختیاری سفارش/سبد/مصرف و ایندکس‌های یکتا را اضافه می‌کند. قیدهای جزئی، بیش از یک تلاش باز یا تسویهٔ موفق برای یک سفارش را رد می‌کنند. مبلغ، وضعیت و مصرف‌های قبلی بازنویسی نمی‌شوند. **این migration با اجازهٔ صریح کاربر روی دیتابیس فعلی با موفقیت اجرا شد.** بررسی فقط‌خواندنی ثبت migration و خواندن PaymentAttempt، DiscountReservation و فیلدهای جدید Order با Prisma موفق بود. دیتابیس طبق `prisma migrate status` به‌روز است. روی دیتابیس دیگر، migration باید قبل از استفاده از کد جدید اجرا شود.

```powershell
npm.cmd run test:unit
npm.cmd run test:payments
npm.cmd run test:discount-codes
npm.cmd run test:order-options
npm.cmd run test:address-contact
npx.cmd playwright test tests/helpers/forms.spec.ts
npm.cmd run lint
npm.cmd run typecheck
npm.cmd run build
```

تست‌های مستقل از دیتابیس، مبلغ، مالکیت، درخواست تکراری/هم‌زمان، callback بدون نشست، ۱۰۱، قطع اتصال پس از verify، نگه‌داشت رزرو، تسویهٔ صفر، ثبت و ابطال دستی و بازقیمت‌گذاری را پوشش می‌دهند. تست PostgreSQL برای migration و رقابت سهمیه فقط با `TEST_DATABASE_URL` و `TEST_DIRECT_URL` روی branch جدا فعال است؛ نبود آن‌ها SKIP است، نه موفقیت آزمون واقعی. تست‌های فرم با دادهٔ مشخص و actionهای شبیه‌سازی‌شده اجرا می‌شوند.

در ۲۰۲۶-۱۱-۰۸، درخواست و inquiry واقعی sandbox و رفت‌وبرگشت Chrome تا callback روی `http://localhost:3328` با موفقیت انجام شد؛ verify موفق، وضعیت PAID و ذخیرهٔ شمارهٔ پیگیری در fixture حافظه تأیید شد. این آزمون پول واقعی یا دیتابیس اصلی را درگیر نکرد و جای آزمون کامل Next + PostgreSQL را نمی‌گیرد.

نتیجهٔ بررسی‌های مستقل: ۷۰ تست واحد و ۱۲ تست پرداخت موفق؛ تست‌های قبلی سرور تخفیف (۴)، ثبت سفارش (۴) و تماس (۲) موفق. فرم نتیجه، بازقیمت‌گذاری، پرداخت دستی، کد تخفیف و انتخاب ارسال در موبایل/دسکتاپ بررسی شدند و تصاویر دو تم بازبینی شدند. lint، typecheck و build موفق‌اند. اتصال فقط‌خواندنی Neon برقرار بود؛ پس از اجرای مجاز migration، `prisma migrate status` هیچ migration در انتظاری گزارش نکرد. تنظیمات محلی نیز SANDBOX، همین UUID تست و `http://localhost:3000` را تأیید کردند.

دستور تکرار بررسی فقط‌خواندنی:

```powershell
node --conditions=react-server --import tsx scripts/verify-payments.ts
```

برای تست دستی خودت، با همان host تنظیم‌شده در PAYMENT_BASE_URL وارد شو، سفارش تازه بساز و «ثبت سفارش و پرداخت» را بزن؛ در درگاه sandbox پرداخت/انصراف را امتحان کن و سپس وضعیت و شمارهٔ پیگیری سفارش را ببین. بازکردن دوبارهٔ callback نباید تسویه یا مصرف جدید ایجاد کند. برای بازگشت به محیط واقعی در آینده، مرچنت فعال و HTTPS لازم است؛ سفارش‌های sandbox قابل تبدیل به سفارش واقعی نیستند.
