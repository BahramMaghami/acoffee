# مدیریت محصولات

`/admin/products` فهرست ۲۰تایی محصول‌های مادر است. ساخت در `/admin/products/new` و ویرایش در `/admin/products/[id]/edit` انجام می‌شود. فرم مشترک کنار صفحهٔ محصولات قرار دارد و با React Hook Form و Zod اعتبارسنجی می‌شود. عملیات در `actions/product.actions.ts` نقش فعلی ADMIN را در سرور و داخل تراکنش بررسی می‌کنند. `updatedAt` مانع ذخیره/حذف از فرم قدیمی می‌شود.

## مدل‌ها و انتقال

- `Category`: نام، slug ثابت، ترتیب و پیش‌فرض‌های دسته. دستهٔ جدید هم‌زمان با محصول و در همان تراکنش ساخته می‌شود.
- `CatalogProduct`: محصول مادر، نام/لینک، دسته، وزن/رست/نوع، نرخ کیلویی هر نوع، تصویر، ترتیب و وضعیت نمایش.
- `Product`: همان SKU قبلی با همان id و slug؛ اکنون به محصول مادر متصل است و رست، نوع، وضعیت سفارش، قیمت نهایی و حالت قیمت دستی دارد. `price=null` یعنی قیمت اعلام نشده.
- `CatalogImport`: رسید انتقال هر محصول قدیمی؛ اجرای مجدد import قیمت‌های ویرایش‌شده را بازنویسی نمی‌کند و محصولی را که مدیر حذف کرده دوباره نمی‌سازد.
- ارتباط سفارش‌ها همچنان با Product است؛ حذف SKU فقط پیوند را null می‌کند. نام، وزن و قیمت ثبت‌شده در OrderItem تغییر نمی‌کنند. اقلام سبد ذخیره‌شده با حذف SKU حذف می‌شوند؛ سبد مرورگر پیام انتخاب ناموجود نشان می‌دهد.

پیش از انتشار این نسخه و زمانی که اتصال Neon برقرار است، به‌ترتیب اجرا شود:

```sh
npm run db:catalog:audit
npm run db:deploy
npm run db:catalog:import
npm run db:status
```

دستور اول فقط‌خواندنی است و اختلاف‌ها را گزارش می‌کند. قیمت دیتابیس بر قیمت آرشیو اولویت دارد و بدون محاسبهٔ مجدد حفظ می‌شود؛ اختلاف وزن، SKU قدیمی ناشناخته یا چند عکس متفاوت در یک محصول مانع انتقال می‌شود. انتقال داده در یک تراکنش انجام می‌شود و به reset یا db push نیاز ندارد. رکوردهای قیمت‌دارِ مفقود، غیرفعال ایجاد می‌شوند؛ موجودی فعال/غیرفعال SKUهای موجود تغییر نمی‌کند. محصولات قبلاً بی‌قیمت همچنان قابل نمایش و غیرقابل پرداخت باقی می‌مانند.

در بررسی زندهٔ `2026-10-23`، تعداد ۱۶۵ SKU موجود بود؛ قیمت و وزن ۱۶۲ انتخاب شناخته‌شده با آرشیو یکسان بود. سه محصول قدیمی `daily-blend`، `single-origin` و `dark-blend` خارج از کاتالوگ فعلی هستند؛ `daily-blend` به یک قلم سفارش متصل است. این سه رکورد بدون تغییر و بدون اتصال به محصول مادر باقی می‌مانند. برای این دیتابیس، فرمان import با فهرست صریح موارد بررسی‌شده اجرا می‌شود:

```sh
npm run db:catalog:import -- --preserve-unmapped=daily-blend,single-origin,dark-blend
```

این گزینه فقط از توقف برای همین slugها جلوگیری می‌کند و آن‌ها را حذف، غیرفعال یا بازنویسی نمی‌کند. رکورد ناشناختهٔ دیگری همچنان انتقال را متوقف می‌کند. به‌روزرسانی SKUها گروهی است تا کندی شبکه باعث صدها رفت‌وبرگشت نشود؛ پیش از پایان تراکنش، حفظ شناسه، slug، قیمت، وزن، وضعیت و تصویر تمام رکوردهای قبلی بررسی می‌شود. migration ساختار نیز با `BEGIN/COMMIT` اتمیک اجرا می‌شود.

خطای `P2021` کاتالوگ به معنی نبود جدول موردنیاز است؛ بعد از تغییر مرجع فروشگاه به دیتابیس، باید migration و import کامل شوند. اتصال برنامه و Prisma CLI مسیرهای متفاوتی دارند. `prisma.config.ts` برای اتصال CLI، در نبود مقدار صریح، `connect_timeout=15` را به `DIRECT_URL` اضافه می‌کند؛ این کار `.env` یا رمزها را تغییر نمی‌دهد. مقدار timeout صریح کاربر حفظ می‌شود. [راهنمای اتصال Neon](https://neon.com/docs/guides/prisma)

انتشار کد جدید باید پس از migration و import موفق باشد؛ نسخهٔ جدید برای خواندن کاتالوگ به جدول‌های جدید نیاز دارد. در زمان انتقال، ویرایش محصولات متوقف باشد. قبل از اعمال روی production از قابلیت بازیابی/branch دیتابیس استفاده شود. migration و import روی Neon در `2026-10-23` اجرا شدند؛ صفحهٔ اصلی با پاسخ ۲۰۰، ۲۳ محصول و ۵ دسته در مرورگر تأیید شد. آزمون سرتاسری مدیریت محصول، خرید و آپلود واقعی همچنان جداگانه باید اجرا شود.

`lib/catalog-fixture.ts` فقط آرشیو انتقال و آزمون قیمت‌های قبلی است. فروشگاه از `lib/catalog.ts` می‌خواند و `lib/storefront.ts` فقط نوع‌ها و کمک‌تابع‌های نمایشی دارد. کوئری فروشگاه با `connection()` فقط در زمان درخواست اجرا می‌شود؛ build به Neon وابسته نیست. seed قدیمی نیز به import محافظت‌شده هدایت شده است.

## فرم و قیمت

- ترتیب: دسته، نام، وزن، رست، نوع، قیمت و عکس؛ وضعیت نمایش کنار ذخیره است.
- خالی‌بودن گزینه‌ها از پیش‌فرض دسته استفاده می‌کند. «بدون رست» با خالی‌بودن فرق دارد. ویرایش با مقادیر ذخیره‌شده باز می‌شود و تغییر دسته انتخاب‌های قبلی را پاک نمی‌کند.
- پیش‌فرض خرده‌فروشی ۲۵۰/۵۰۰/۱۰۰۰ گرم و عمده ۵/۱۰ کیلو است. ترکیبی، عمده و دستهٔ جدید دو نوع Commercial/Premium دارند؛ تک‌دان، سنتی و نسکافه یک نوع. سنتی و نسکافه رست ندارند.
- قیمت‌ها تومان صحیح‌اند؛ ارقام فارسی/عربی پذیرفته می‌شوند. نرخ یک کیلو برای هر نوع و قیمت مستقل هر انتخاب قابل ثبت است. رست‌ها در حالت محاسباتی نرخ مشترک دارند.
- ۱۰ کیلوی عمده از دو برابر قیمت نهایی ۵ کیلو، منهای ۳٪ محاسبه می‌شود. قیمت مستقل ۱۰ کیلو اولویت دارد. وقتی وزن ۵ کیلو عرضه نشود، نرخ کیلویی مبناست.
- محاسبات با BigInt و گردکردن نیم به بالا انجام می‌شود. قیمت مستقل خالی یعنی «اعلام نشده»؛ دکمهٔ «بازگشت به محاسبه» override را حذف می‌کند. برای ساخت محصول جدید همهٔ انتخاب‌ها باید قیمت مثبت داشته باشند.
- قیمت‌های منتقل‌شده دستی‌اند؛ تغییر نرخ پایه تا وقتی override حذف نشود روی آن‌ها اثر ندارد. نشان تاریخی ۳٪ برای انتخاب‌های قدیمی حفظ می‌شود؛ نشان محصولات جدید از فرمول واقعی می‌آید.
- کنترل «قابل سفارش» هر ردیف وضعیت SKU را حفظ/تغییر می‌دهد؛ کنترل نمایش محصول کل محصول را پنهان می‌کند. قیمت و هر دو وضعیت در checkout دوباره بررسی می‌شوند.
- تغییر نام، slug را تغییر نمی‌دهد. حذف وزن/رست/نوع نیاز به تأیید داخل صفحه دارد. تاریخچهٔ سفارش مستقل است.

## تصاویر Cloudinary

متغیرهای زیر را در `.env` و محیط اجرای هاست قرار دهید؛ کلید محرمانه فقط سمت سرور است:

```dotenv
CLOUDINARY_CLOUD_NAME=
CLOUDINARY_API_KEY=
CLOUDINARY_API_SECRET=
```

پس از تنظیم، برنامه restart/redeploy شود. عکس بدون کلیدها اختیاری باقی می‌ماند و تصاویر فعلی روشن/تیره استفاده می‌شوند. تصویر اختصاصی در هر دو تم یکسان است. عکس JPG/PNG/WebP ثابت و حداکثر ۵ مگابایت پذیرفته می‌شود.

Server Action فقط برای مدیر امضای آپلود و شناسهٔ تصادفی در `acoffee/products/` صادر می‌کند. مجوز HMAC به همان مدیر و همان public ID محدود است و یک ساعت اعتبار دارد. پیش از اتصال تصویر، سرور با Cloudinary نوع، اندازه، شناسه و آدرس امن را بررسی می‌کند. پارامترهای آپلود اجازهٔ overwrite نمی‌دهند. پس از ذخیره/حذف موفق، تصویر قبلیِ بدون ارجاع پاک می‌شود؛ خطای پاکسازی ثبت می‌شود و تغییر موفق دیتابیس را شکست‌خورده نشان نمی‌دهد. فایل‌های رهاشده در فرم ذخیره‌نشده فعلاً خودکار پاک نمی‌شوند و در پوشهٔ Cloudinary قابل بررسی‌اند.

## تست

```sh
npm run test:unit
npm run test:images
npm run typecheck
npm run build
```

تست تصاویر، امضای آپلود، مجوز وابسته به مدیر، نوع و اندازهٔ فایل و پاسخ نامعتبر سرویس را با پاسخ‌های شبیه‌سازی‌شده بررسی می‌کند؛ آپلود واقعی انجام نمی‌دهد.

پس از برقرارشدن اتصال و اعمال انتقال:

```powershell
$env:ADMIN_PRODUCTS_E2E='1'
npx.cmd playwright test tests/ui/admin-products.spec.ts --project=desktop
```

تست زنده با حساب، دسته، محصول و سفارش اختصاصی کار می‌کند و آن‌ها را پاک می‌کند. ساخت و ویرایش، صفحهٔ فروشگاه، checkout، فرم قدیمی، تأیید حذف انتخاب‌ها، غیرفعال‌سازی و حفظ تاریخچه پس از حذف را بررسی می‌کند. تست مهمان بدون متغیر بالا هم اجرا می‌شود. آپلود واقعی به تنظیمات Cloudinary و اتصال سرویس نیاز دارد.
