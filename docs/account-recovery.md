# حساب مشتری و تثبیت محصولات

نام و آدرس جاری از `/account` ویرایش می‌شوند؛ ایمیل ورود ثابت است. آدرس حساب و checkout یک رکورد جاری مشترک دارند و snapshot سفارش‌های قبلی تغییر نمی‌کند. تغییر نام، نام گیرندهٔ آدرس جاری و هدر را هم به‌روز می‌کند.

## پیش‌نیاز دیتابیس

این تغییر به migration `20261026000000_account_recovery` نیاز دارد: افزودن `User.sessionVersion` و جدول `PasswordResetToken`. تولید Prisma Client به‌تنهایی migration را اجرا نمی‌کند. نسخهٔ جدید ورود و حساب را پیش از اعمال این migration روی محیط هدف منتشر نکنید.

ابتدا یک branch **جدا و خالی** در Neon و متغیرهای `TEST_DATABASE_URL` و `TEST_DIRECT_URL` فراهم کنید. دستور `npm run db:prepare:test` فقط همان مقصد آزمایشی را migrate می‌کند و دادهٔ ثابت تست می‌سازد. اگر داده‌ای وجود داشته باشد، seed از بازنویسی آن خودداری می‌کند؛ fixture آماده‌شده را بدون اجرای دوبارهٔ seed استفاده کنید. پس از موفقیت آزمون‌ها، migration افزایشی با `npm run db:deploy` روی محیط هدف اعمال شود؛ reset یا seed عمومی لازم نیست.

**وضعیت ۲۰۲۶-۱۱-۰۱:** با اجازهٔ صریح کاربر برای رفع خرابی ورود، همین migration با `prisma migrate deploy` روی دیتابیس فعلی اجرا شد. ثبت موفق migration و خواندن `User.sessionVersion` و `PasswordResetToken` از طریق Prisma تأیید شدند. تست نوشتنی روی دیتابیس اصلی، reset یا seed اجرا نشد. دیتابیس آزمایشی و SMTP هنوز تنظیم نشده‌اند؛ آزمون‌های وابسته به آن‌ها همچنان باقی‌اند. نتیجهٔ مورخ ۲۰۲۶-۱۰-۲۶ در انتهای این سند، سابقهٔ پیش از این اجراست.

## ارسال بازیابی رمز

`SMTP_HOST`، `SMTP_PORT`، `SMTP_USER`، `SMTP_PASS`، `SMTP_FROM` و `AUTH_URL` را در محیط اجرا تنظیم کنید. `SMTP_FROM` باید فرستندهٔ مجاز سرویس ایمیل باشد. `AUTH_URL` فقط origin کامل HTTPS مانند `https://shop.example.com` است؛ مسیر، query و اطلاعات ورود پذیرفته نمی‌شوند. برای توسعه، HTTP فقط روی localhost مجاز است.

پورت ۴۶۵ از TLS مستقیم و پورت‌های دیگر production از STARTTLS اجباری استفاده می‌کنند. اتصال loopback در توسعه برای گیرندهٔ SMTP تست بدون احراز هویت/TLS مجاز است. سرویس با SMTP قابل تعویض است؛ انتخاب سرویس داخلی به معنی تضمین دسترسی کاربر به صندوق ایمیل خارجی هنگام اختلال اینترنت نیست.

بدون تنظیمات معتبر، بازیابی صریحاً غیرفعال است. درخواست معتبر پاسخ عمومی یکسان می‌گیرد؛ بررسی وجود حساب و ارسال با `after()` پس از پاسخ انجام می‌شوند تا زمان SMTP وجود حساب را افشا نکند. «درخواست دریافت شد» تأیید تحویل ایمیل نیست. ارسال best-effort است و صف پایدار ندارد؛ در خطای ارسال، توکن همان درخواست حذف، خطا بدون دادهٔ حساس ثبت و درخواست مجدد ممکن می‌شود. هاست باید اجرای `after()` و حداکثر زمان مسیر ۶۰ ثانیه را پشتیبانی کند.

توکن تصادفی ۳۲‌بایتی، ۳۰ دقیقه اعتبار دارد و فقط هش آن ذخیره می‌شود. GET لینک را مصرف نمی‌کند. تغییر رمز، افزایش نسخهٔ نشست و حذف همهٔ توکن‌های آن کاربر تراکنشی است. نشست‌های قدیمی بدون نسخه صفر محسوب می‌شوند و پس از تغییر رمز دیگر به عملیات محافظت‌شده دسترسی ندارند. محدودیت درخواست بازیابی ۳ بار در ساعت برای هر ایمیل و تغییر رمز ۸ بار در ۱۵ دقیقه برای هر حساب است؛ رسیدن به حد، خود حساب را قفل نمی‌کند.

لاگ Server Action و ثبت درخواست مسیر reset در Next خاموش است. در reverse proxy، سرویس مانیتورینگ و هاست نیز query مسیر `/reset-password` و بدنهٔ فرم‌های رمز را ثبت نکنید. صفحات بازیابی `no-store`، `noindex` و `no-referrer` دارند.

## آزمون‌ها

- `npm run test:unit`: قیمت، ورودی‌ها، نسخهٔ نشست و محافظ مقصد تست؛ بدون نوشتن دیتابیس.
- `npm run test:images`: اعتبارسنجی تصویر با سرویس شبیه‌سازی‌شده.
- `npm run test:mail`: ارسال و شکست ارسال به گیرندهٔ SMTP محلی؛ هیچ ایمیل خارجی ارسال نمی‌شود.
- `npx playwright test tests/helpers/forms.spec.ts`: فرم‌های واقعی با مرز ذخیره‌سازی شبیه‌سازی‌شده، موبایل و دسکتاپ، دو تم و خطای شبکه؛ اثبات‌کنندهٔ ذخیرهٔ واقعی دیتابیس نیست.
- `npm run test:recovery`: تراکنش بازیابی، مصرف هم‌زمان توکن و محدودیت تلاش در دیتابیس آزمایشی؛ بدون تنظیمات تست، صریحاً skip می‌شود.
- با `ACCOUNT_E2E=1` و `ADMIN_PRODUCTS_E2E=1`، اجرای `npx playwright test tests/helpers/account.spec.ts tests/ui/admin-products.spec.ts` حساب و مسیر محصول تا سفارش را در branch آزمایشی بررسی می‌کند. تست حساب SMTP را روی loopback پورت ۳۳۲۵ اجرا می‌کند.
- تست‌های storefront/theme/ribbon به fixture حاصل از `db:prepare:test` وابسته‌اند؛ تغییر محصولات واقعی نباید نتایج آن‌ها را عوض کند. سایر تست‌های نوشتنی نیز تنها متغیرهای `TEST_*` را می‌پذیرند.

Playwright یک سرور مجزا روی پورت ۳۳۱۰ با خروجی `artifacts/next-test` اجرا می‌کند و سرور توسعهٔ معمولی را دوباره استفاده نمی‌کند. حتی بدون دیتابیس آزمایشی، اتصال اصلی در محیط این سرور خالی می‌شود. گزارش‌های تست حاوی حساب آزمایشی‌اند؛ trace و عکس خودکار تست‌های احراز هویت خاموش است.

## قیمت نامعتبر و قطع شبکه

ردیف‌های پیش‌نمایش مستقل از اعتبار قیمت باقی می‌مانند. خطا کنار ورودی نمایش داده می‌شود و فقط ردیف‌های وابسته محاسبه‌نشده‌اند؛ قیمت دستی ۱۰ کیلو از قیمت نامعتبر ۵ کیلو مستقل است. مبلغ خالیِ دستی همچنان «اعلام نشده» است؛ دکمهٔ بازگشت به محاسبه کلید override را حذف می‌کند. محاسبات نهایی سرور، قیمت‌های منتقل‌شده و قواعد تخفیف تغییر نکرده‌اند.

ذخیره/آپلود ناموفق فرم را پاک نمی‌کند. خطای تعارض ویرایش با خطای اتصال فرق دارد. قیمت‌ها، SKUها و سفارش‌های واقعی در این مرحله دستکاری نشده‌اند.

## نتیجهٔ بررسی ۲۰۲۶-۱۰-۲۶

- ۴۷ تست واحد، ۴ تست تصاویر شبیه‌سازی‌شده و ۱ تست SMTP محلی موفق شدند.
- ۱۰ تست مرورگری روی build واقعی production موفق شدند: رگرسیون فرم قیمت، فرم‌های حساب و بازیابی، حفظ ورودی هنگام خطا، تم روشن/تیره، موبایل/دسکتاپ، منع ورود مهمان به مدیریت محصولات و هدرهای امنیتی بازیابی. تصاویر فرم‌ها نیز بررسی شدند. ذخیره‌سازی فرم‌ها در تست مستقل شبیه‌سازی شده بود.
- `typecheck`، `build`، اعتبارسنجی Prisma و lint بدون خطا موفق بودند. تنها هشدار lint مربوط به متغیر استفاده‌نشدهٔ قبلی در `zarinpal.ts` است که خارج از محدوده باقی ماند.
- ۴ مورد مرورگری وابسته به دیتابیس و تست تراکنشی بازیابی skip شدند؛ تنظیمات branch آزمایشی فراهم نبود. این نتایج تأیید ذخیرهٔ واقعی، مصرف هم‌زمان توکن یا تحویل ایمیل از سرویس production نیستند.
- migration روی دیتابیس اصلی اجرا نشده و SMTP واقعی تنظیم نشده است. اعمال migration پس از آزمون branch و تنظیم SMTP، پیش‌نیاز فعال‌سازی کامل‌اند. هیچ کامیتی ایجاد نشد.

در حالت توسعه، Next هدر کش را به `no-cache, must-revalidate` تغییر می‌دهد. بررسی `no-store` روی `next start` انجام شد؛ برای تکرار آن ابتدا با `ACOFFEE_E2E=1` خروجی production تست را build کنید و سپس با `ACOFFEE_TEST_PRODUCTION=1` تست مرورگری را اجرا کنید. تست واقعی SMTP/حساب با سرور development و گیرندهٔ محلی اجرا می‌شود؛ production به تنظیمات امن و فرستندهٔ واقعی نیاز دارد.
