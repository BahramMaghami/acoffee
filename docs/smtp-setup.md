# راه‌اندازی ایمیل بازیابی رمز آ

کد ارسال فارسی، لینک یک‌بارمصرف ۳۰ دقیقه‌ای، محدودیت درخواست و ابطال نشست‌های قبلی آماده است. migration حساب نیز اجرا شده است. برای ارسال واقعی باید یک سرویس SMTP و دامنهٔ فرستندهٔ تأییدشده داشته باشیم. تا پیش از تنظیم آن‌ها، بازیابی رمز پیام «فعلاً در دسترس نیست» دارد؛ ورود عادی وابسته به SMTP نیست.

## کارهایی که صاحب سایت انجام می‌دهد

### ۱. ساخت حساب سرویس ارسال ایمیل

کد به سرویس خاصی وابسته نیست؛ هر سرویس SMTP با نام کاربری/رمز و TLS قابل استفاده است. یک گزینهٔ سازگار **Resend** است. نمونهٔ زیر برای این سرویس نوشته شده؛ تهیهٔ حساب و انتخاب پلن با صاحب سایت است.

در پنل سرویس، دامنهٔ `acoffeeroasters.com` را اضافه کن. رکوردهای DNS مربوط به ارسال و DKIM/SPF را **دقیقاً طبق مقادیر پنل خودت** در محل مدیریت DNS دامنه وارد کن و منتظر وضعیت Verified بمان. رکوردهای وب‌سایت یا دریافت ایمیل موجود را حذف نکن. برای بازیابی رمز، click tracking و open tracking را خاموش نگه دار.

تأیید دامنهٔ ایمیل مستقل از اینماد است؛ نشان اینماد، دامنهٔ فرستنده را تأیید نمی‌کند. سرویس ارسال هم الزاماً صندوق دریافت ایمیل برایت نمی‌سازد.

راهنمای رسمی: [دامنه‌های Resend](https://resend.com/docs/dashboard/domains/introduction).

### ۲. ساخت کلید و تنظیم متغیرها

در Resend یک API Key با مجوز ارسال برای دامنهٔ تأییدشده بساز. مقدار کلید را فقط در `.env.local` یا `.env` محلی و بخش Environment Variables هاست بگذار؛ در چت، کد یا Git قرار نده. هیچ‌کدام از متغیرها نباید پیشوند `NEXT_PUBLIC_` داشته باشند.

نمونهٔ production برای Resend:

```dotenv
AUTH_URL="https://acoffeeroasters.com"
SMTP_HOST="smtp.resend.com"
SMTP_PORT=465
SMTP_USER="resend"
SMTP_PASS="REPLACE_WITH_RESEND_API_KEY"
SMTP_FROM="آ <noreply@acoffeeroasters.com>"
```

اگر یک زیردامنه مانند `mail.acoffeeroasters.com` را تأیید کرده‌ای، فرستنده هم باید روی همان زیردامنه باشد. `AUTH_URL` همچنان آدرس خود فروشگاه است. برای سرویس دیگری، host/port/user/pass را از همان سرویس بگیر.

پورت ۴۶۵ در کد TLS مستقیم دارد؛ پورت ۵۸۷ به STARTTLS نیاز دارد. اعتبار گواهی TLS بررسی می‌شود. از پورت جایگزین دارای implicit TLS مثل ۲۴۶۵ بدون تغییر تنظیم کد استفاده نکن.

برای توسعهٔ محلی، `AUTH_URL="http://localhost:3000"` بگذار تا لینک به همان محیط و دیتابیس توسعه برگردد. رمز فراموش‌شده را در یک محیط درخواست کن و در همان محیط باز کن؛ توکن یک دیتابیس روی دیتابیس دیگر معتبر نیست. پس از تغییر env، سرور توسعه را restart و نسخهٔ هاست را redeploy کن. `.env` محلی خودکار روی هاست منتقل نمی‌شود.

راهنمای رسمی: [تنظیم SMTP در Resend](https://resend.com/docs/send-with-smtp).

### ۳. بررسی اتصال بدون ارسال ایمیل

```sh
npm run smtp:verify
```

این دستور از تنظیمات shell/هاست و سپس `.env.local` و `.env` استفاده می‌کند؛ متغیرهای shell اولویت دارند. فایل‌های دیگر مثل `.env.production` را خودکار بارگذاری نمی‌کند. دستور به دیتابیس وصل نمی‌شود، توکن نمی‌سازد و هیچ ایمیلی ارسال نمی‌کند. مقدار رمز، کلید و پاسخ خام SMTP در خروجی چاپ نمی‌شود.

موفقیت یعنی اتصال، مذاکرهٔ TLS و احراز هویت SMTP موفق بوده‌اند؛ معتبر بودن آدرس فرستنده یا رسیدن ایمیل به Inbox را اثبات نمی‌کند. این بررسی را در محیط هاست نیز انجام بده؛ موفقیت روی لپ‌تاپ، دسترسی شبکهٔ سرور را تضمین نمی‌کند.

### ۴. آزمون واقعی بازیابی

پس از انتشار تنظیمات، با یک حساب تحت کنترل خودت در `/forgot-password` درخواست بازیابی بده. Inbox و Spam و بخش Emails سرویس را بررسی کن. لینک باید روی دامنهٔ صحیح به `/reset-password` برسد. تعیین رمز جدید باید ورود با رمز جدید را ممکن و نشست‌های قدیمی را نامعتبر کند؛ همان لینک بار دوم پذیرفته نشود.

پاسخ عمومی «درخواست دریافت شد» به‌تنهایی تأیید ارسال نیست. برای جلوگیری از افشای وجود حساب، این پاسخ برای ایمیل موجود و ناموجود یکسان است. سه درخواست در ساعت برای هر ایمیل مجاز است. اگر ایمیل نرسید، لاگ امن `recovery-delivery` سرور و گزارش سرویس ارسال را بررسی کن؛ توکن و لینک خام را در لاگ نگذار.

## آزمون‌های پروژه و وضعیت فعلی

- `npm run test:mail`: SMTP محلی، بررسی اتصال بدون ارسال، محتوای لینک و شکست ارسال؛ بدون ایمیل خارجی یا دیتابیس.
- `npm run test:unit`: قواعد رمز، تنظیمات امن SMTP و نسخهٔ نشست، به‌همراه سایر تست‌های واحد.
- آزمون کامل ذخیره و مصرف هم‌زمان توکن به `TEST_DATABASE_URL` و `TEST_DIRECT_URL` روی دیتابیس جدا نیاز دارد؛ دیتابیس اصلی جایگزین خودکار نیست.
- در این مرحله حساب SMTP، رکورد DNS، API key و فرستندهٔ واقعی ساخته نشده‌اند و تحویل واقعی ایمیل تأیید نشده است. کد ارسال از `after()` استفاده می‌کند و صف پایدار ندارد؛ خطای ارسال نیازمند درخواست مجدد است.

مبنای بررسی اتصال: [Nodemailer SMTP](https://nodemailer.com/smtp).
