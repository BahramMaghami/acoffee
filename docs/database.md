# دیتابیس acoffee — مرحلهٔ اول

Prisma 7، PostgreSQL و adapter اختصاصی Neon. مرحلهٔ فعلی شامل اسکیما، کلاینت و migration است؛ اجرای migration روی Neon به تنظیم اتصال واقعی نیاز دارد.

## راه‌اندازی

1. وابستگی‌ها را با `npm ci` نصب کنید.
2. فایل `.env.example` را به `.env` در ریشهٔ پروژه کپی کنید.
3. از بخش Connect در Neon، آدرس pooled را در `DATABASE_URL` و آدرس direct همان دیتابیس و branch را در `DIRECT_URL` قرار دهید. تنظیم TLS آدرس‌های Neon را حفظ کنید. فایل `.env` نباید commit شود.
4. با `npm run db:validate` اسکیما را بررسی و با `npm run db:deploy` migration ثبت‌شده را اجرا کنید.
5. با `npm run db:status` وضعیت migration و با `npm run db:studio` داده‌ها را بررسی کنید.

`npm ci` و `npm run build`، Prisma Client را تولید می‌کنند. تولید کلاینت و بررسی اسکیما به اتصال دیتابیس نیاز ندارند. Prisma CLI از `.env` با dotenv استفاده می‌کند؛ آدرس‌ها را فقط در `.env.local` نگذارید.

برای تغییرات بعدی اسکیما، روی branch توسعهٔ Neon از `npm run db:migrate -- --name description` استفاده کنید و SQL تولیدشده را پیش از commit بررسی کنید. migrationهای ثبت‌شده را با `db:deploy` اعمال کنید. CHECKهای سفارشی در SQL نوشته شده‌اند؛ از `db push` به‌جای migration استفاده نکنید.

## کاربران اولیه

بعد از `npm run db:deploy` دستور `npm run db:seed` را اجرا کنید. مطابق [رفتار Prisma 7](https://www.prisma.io/docs/orm/v6/prisma-migrate/workflows/seeding)، seed جداگانه اجرا می‌شود.

| نام | ایمیل ورود | نقش |
| --- | --- | --- |
| admin | admin@acoffee.test | ADMIN |
| bahram | bahram@acoffee.test | CUSTOMER (کاربر عادی) |

رمزهای اولیه به‌صورت تصادفی تولید و در فایل محلی `.seed-users.local.json` ذخیره می‌شوند؛ این فایل در Git نادیده گرفته می‌شود. در دیتابیس فقط هش bcrypt با cost برابر ۱۲ ذخیره می‌شود. احراز هویت آینده باید از `bcryptjs.compare` برای بررسی این رمزها استفاده کند.

اجرای دوبارهٔ seed کاربر تکراری نمی‌سازد و نام، نقش یا رمز کاربر موجود را تغییر نمی‌دهد. اگر کاربر موجود با نقش/نام seed متفاوت باشد یا رمز محلی دیگر با دیتابیس مطابقت نداشته باشد، seed خطا می‌دهد. این ایمیل‌ها آزمایشی‌اند و برای ارسال ایمیل استفاده نمی‌شوند.

برای مشاهدهٔ مدل `User` و دیگر جدول‌ها، `npx prisma studio` را در ریشهٔ پروژه اجرا کنید.

## مدل‌ها

| مدل | کاربرد |
| --- | --- |
| `User` | نام، ایمیل یکتا، هش رمز، نقش مشتری/مدیر و ارتباط با آدرس، سبد و سفارش |
| `Address` | دفترچهٔ آدرس کاربر؛ آدرس نهایی هنگام خرید در سفارش کپی می‌شود |
| `Product` | مشخصات قهوه، قیمت، موجودی، وزن بسته به گرم، تصویر اختیاری و وضعیت فعال |
| `Cart` | یک سبد برای هر کاربر، یا سبد مهمان با هش توکن تصادفی و تاریخ انقضا |
| `CartItem` | تعداد هر محصول؛ یک ردیف برای هر جفت سبد/محصول |
| `Order` | شمارهٔ سفارش، وضعیت سفارش و پرداخت، مبالغ و کپی مستقل آدرس ارسال |
| `OrderItem` | کپی نام، slug، وزن و قیمت محصول هنگام خرید، تعداد و جمع ردیف |

## قراردادهای داده

- واحد فعلی تمام مبالغ **تومان** است؛ از `Decimal(14, 0)` استفاده می‌شود. `price` جایگزین نام مبهم `value` است. محاسبات مالی با `Prisma.Decimal` انجام می‌شوند و مبالغ هنگام ارسال به کلاینت به رشته تبدیل می‌شوند. تبدیل واحد درگاه در مرز اتصال به درگاه انجام می‌شود.
- هر محصول یک بسته با وزن مشخص است. تنوع وزن فعلاً با محصول جدا تعریف می‌شود.
- زمان‌ها با `timestamptz` و مبتنی بر زمان میلادی ذخیره می‌شوند. نمایش و ورود شمسی با util مشترک در مرحلهٔ UI پیاده می‌شود.
- ایمیل قبل از ذخیره و جست‌وجو باید trim و lowercase شود؛ CHECK دیتابیس این قرارداد را هنگام ذخیره enforce می‌کند.
- `passwordHash` برای هش رمز است. کلاینت مشترک آن را به‌صورت پیش‌فرض از نتایج حذف می‌کند؛ auth برای بررسی رمز باید آن را صریحاً select کند. خروجی عمومی کاربر همچنان باید با DTO محدود شود.
- سبد دقیقاً یک مالک دارد: `userId` یا `guestTokenHash`. توکن خام مهمان فقط در کوکی امن نگه‌داری می‌شود. بررسی انقضا، پاک‌سازی سبدهای منقضی و ادغام سبد پس از ورود در مرحلهٔ سبد پیاده می‌شوند.
- محصولات ترجیحاً غیرفعال می‌شوند. حذف محصول، ردیف‌های سبد را حذف می‌کند و مشخصات ثبت‌شده در سفارش را نگه می‌دارد. حذف کاربر دارای سفارش و حذف سفارش دارای اقلام محدود شده است.
- CHECKهای migration، مبالغ و موجودی غیرمنفی، تعداد و وزن مثبت، مالکیت سبد و سازگاری جمع مبالغ هر ردیف و سفارش را بررسی می‌کنند. مجموع اقلام سفارش باید داخل transaction در سمت سرور محاسبه شود؛ این رابطهٔ بین چند ردیف با CHECK کنترل نمی‌شود.
- مدل مستقل `Payment` برای تلاش‌های پرداخت، شناسهٔ درگاه و idempotency در مرحلهٔ اتصال به درگاه اضافه خواهد شد؛ وضعیت پرداخت فعلی جایگزین آن نیست.

## بررسی‌ها

```bash
npm run db:validate
npm run db:generate
npm run typecheck
npm run lint
npm run build
```

اعتبارسنجی اسکیما و build به‌تنهایی اتصال Neon یا اجرای SQL روی PostgreSQL را اثبات نمی‌کنند؛ برای آن‌ها `db:deploy` و `db:status` باید با آدرس واقعی اجرا شوند.
