# شمارهٔ حساب — اجرای مرحله‌ای

## مرحلهٔ ۱: ثبت اولین شمارهٔ تأییدشده

در `/account` شماره و تاریخ تأیید نمایش داده می‌شوند. اگر شماره تأیید نشده باشد، فرم React Hook Form/Zod شمارهٔ ایران و رمز فعلی را می‌گیرد، سپس کد شش‌رقمی کاوه‌نگار را تأیید می‌کند. مدیر همین شماره را در فهرست کاربران موجود می‌بیند. شمارهٔ حساب مستقل از آدرس ارسال است و چند حساب می‌توانند شمارهٔ یکسان داشته باشند.

کد دو دقیقه اعتبار و پنج فرصت بررسی دارد. ارسال مجدد فاصلهٔ اجباری ندارد؛ سهمیهٔ شماره/ایمیل (۲۰ ارسال در ساعت) و کل ارسال (۲۰۰ در ۲۴ ساعت) با ثبت‌نام مشترک است. بررسی رمز همچنان هشت تلاش در پانزده دقیقه برای هر حساب دارد و ممکن است زودتر از سهمیهٔ پیامک، درخواست این فرم را محدود کند. ارسال ناموفق هم سهمیه مصرف می‌کند. کد خام و رمز لاگ نمی‌شوند؛ فقط HMAC متصل به هدف، شناسهٔ درخواست، کاربر، نسخهٔ نشست و شماره ذخیره می‌شود.

هویت از نشست معتبر سرور می‌آید. مرحلهٔ درخواست رمز فعلی را بررسی می‌کند؛ تأیید زیر قفل ردیف User انجام می‌شود و با ارسال مجدد و تغییر رمز هم‌زمان سازگار است. تغییر نسخهٔ نشست، کد قبلی را باطل می‌کند. حساب دارای شمارهٔ تأییدشده از هر دو action رد می‌شود؛ تغییر شماره در این مرحله مجاز نیست. شکست ارسال، درخواست را در حالت ارسال‌نشده نگه می‌دارد. فرم هنگام خطا باقی می‌ماند.

### migration و تنظیمات

- تنظیمات همان `KAVENEGAR_API_KEY`، `KAVENEGAR_OTP_TEMPLATE` و `OTP_SECRET` ثبت‌نام هستند؛ کلید جدیدی لازم نیست.
- migration `20261103010000_account_phone_otp` فقط جدول `AccountPhoneOtp`، ایندکس‌ها و ارتباط با User را اضافه می‌کند. جدول مستقل از ثبت‌نام است؛ دادهٔ موجود تغییر نمی‌کند.
- کاربر اجرای همین migration روی دیتابیس فعلی را صریحاً تأیید کرد. `npm run db:deploy` با دسترسی شبکه اجرا شد، اما پیش از گزارش اعمال موفق با `Schema engine error` متوقف شد. `db:status` نیز همین خطا را داد و بررسی فقط‌خواندنی جدول/تاریخچه از HTTPS Neon با `NeonDbError` ناموفق بود؛ اعمال migration هنوز تأیید نشده و ادامه منتظر اتصال سالم است. مجوز کاربر برای همین migration برقرار است و نیازی به اجازهٔ مجدد ندارد. `TEST_DATABASE_URL` و `TEST_DIRECT_URL` همچنان تنظیم نیستند؛ تست نوشتنی روی دیتابیس اصلی اجرا نشده است.
- پس از اعمال migration و تولید Prisma Client، سرور محلی را دوباره راه‌اندازی کن. تا اعمال migration، نمایش حساب کار می‌کند اما درخواست تأیید شماره قابل استفاده نیست.

### آزمون

`npm run test:unit` اعتبارسنجی و اتصال هش به هویت را بررسی می‌کند. `npm run test:account-phone` مهمان و جعل هویت در action را با وابستگی‌های شبیه‌سازی‌شده بررسی می‌کند؛ تست تراکنش‌ها، اشتراک شماره، انقضا، تلاش اشتباه، مصرف هم‌زمان و ابطال نشست فقط روی branch آزمایشی اجرا می‌شود و بدون تنظیمات آن skip است.

`npx playwright test tests/helpers/forms.spec.ts --grep 'account phone|signup'` فرم واقعی را با action شبیه‌سازی‌شده در موبایل و دسکتاپ، دو تم، خطای شبکه و حفظ ورودی بررسی می‌کند. هیچ‌یک از این تست‌ها پیامک واقعی ارسال نمی‌کنند.

نتیجهٔ این نوبت: ۵۲ تست واحد، تست کنترل هویت action، تست SDK و چهار تست مرورگری موفق شدند. بعد از اصلاح فاصلهٔ دکمه‌ها، دو تست شمارهٔ حساب و تصاویر هر دو تم دوباره بررسی شدند. schema، typecheck و build معتبرند؛ lint فقط هشدار قدیمی `zarinpal.ts` دارد. تأیید عملی تراکنش‌های دیتابیس و پیامک واقعی همچنان باقی است.

پس از migration، برای تست دستی با حساب قدیمی بدون شمارهٔ تأییدشده وارد `/account` شو: رمز نادرست را امتحان کن، سپس با رمز درست کد بگیر، یک کد اشتباه و بعد کد درست را وارد کن؛ صفحه را تازه کن و ثبت شماره را در `/admin/users` بررسی کن. حسابی که هنگام ثبت‌نام شماره را تأیید کرده، فقط شمارهٔ تأییدشده را می‌بیند.

## مراحل بعدی — هنوز اجرا نشده

۲. تغییر شمارهٔ تأییدشده با رمز فعلی و کد شمارهٔ جدید.

۳. ورود اختیاری مشتری با ایمیل و OTP؛ ورود مدیر با رمز باقی می‌ماند.

مرحلهٔ ۴ در ۲۰۲۶-۱۱-۰۶ با درخواست جدید کاربر پیاده شد: الزام شمارهٔ تأییدشده پیش از سفارش، شمارهٔ اصلی ثابت و شمارهٔ تماس جایگزین اختیاری در آدرس و سفارش. وضعیت migration و آزمون‌ها در [راهنمای تماس سفارش](address-contact.md) ثبت شده است.

پس از هر مرحله، اجرا برای تست صاحب پروژه متوقف می‌شود. هیچ کامیتی در این نوبت ایجاد نشده است.
