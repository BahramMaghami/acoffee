# انتقال Neon به PostgreSQL هاست

## وضعیت

بکاپ ۱۶ نوامبر روی PostgreSQL 16.15 بازیابی شده و تعداد رکوردهای ۲۸ جدول برابر است.
این مقصد هنوز مرجع سایت نیست و داده‌های بعد از بکاپ را ندارد. تطبیق تعداد، اثبات یکسان‌بودن تمام محتوای داده‌ها نیست.

## اتصال کد

`lib/database-adapter.ts` برای hostnameهای منتهی به `.neon.tech` همان PrismaNeon قبلی را نگه می‌دارد؛ سایر آدرس‌های PostgreSQL از PrismaPg استفاده می‌کنند. URL نامعتبر یا خالی خطا می‌دهد و fallback به دیتابیس دیگری وجود ندارد. TLS از URL پیروی می‌کند. حداکثر اتصال هر پردازش ۵ است.

کد را می‌توان قبل از انتقال با URL فعلی Neon منتشر کرد. seed و ابزار انتقال کاتالوگ نیز از همین انتخاب adapter استفاده می‌کنند؛ هنگام انتقال دیتابیس هیچ seed یا import کاتالوگی اجرا نکنید.

## بررسی مقصد از ویندوز

تونل SSH روی `127.0.0.1:55432` باز باشد. فایل ignored با نام `.env.db-host` فقط برای بررسی مقصد بسازید:

```dotenv
DATABASE_URL="postgresql://acoffeer_acoffeeapp:URL_ENCODED_PASSWORD@127.0.0.1:55432/acoffeer_acoffee?sslmode=disable"
```

رمز باید percent-encoded باشد، خصوصاً کاراکترهای @، #، %، $ و :. این آدرس فقط برای تونل محلی است؛ ارتباط بیرونی را SSH رمزنگاری می‌کند. فایل را commit یا در چت ارسال نکنید. این فایل به‌طور خودکار توسط Next بارگذاری نمی‌شود.

```powershell
node --import tsx scripts/check-postgres.ts .env.db-host
```

این ابزار فقط همان فایل صریح را می‌خواند و تمام queryها را در تراکنش READ ONLY اجرا می‌کند؛ خروجی فقط نسخه و تعدادهاست، بدون اطلاعات مشتریان. برای تست UI با کپی داده‌های واقعی، ارسال پیامک/ایمیل و پرداخت واقعی را فعال نکنید.

## جابه‌جایی نهایی (هنوز اجرا نشده)

1. نسخهٔ جدید کد را با اتصال Neon build و آماده کنید؛ زمان وقفهٔ کوتاه را تعیین کنید.
2. ابتدا سفارش و پرداخت جدید را متوقف کنید؛ callback و reconciliation باید تا تعیین تکلیف پرداخت‌های فعال کار کنند. اگر وضعیت نامشخص باقی است، قطع اتصال به مبدأ را عقب بیندازید.
3. پس از تعیین تکلیف پرداخت‌ها، تمام نویسنده‌ها از جمله تغییرات مدیر، ثبت‌نام، cron و پردازش‌های پس‌زمینه را متوقف کنید. صرفاً خاموش‌کردن دکمهٔ خرید کافی نیست.
4. از Neon بکاپ تازه بگیرید و اصل آرشیو را خارج از public_html حفظ کنید. فایل سازگار قبلی را برای بکاپ جدید کپی نکنید؛ فهرست اشیا و وابستگی‌ها باید دوباره بررسی شوند. pg_session_jwt منتقل نمی‌شود؛ داده‌های neon_auth حفظ می‌شوند ولی سرویس مدیریت‌شدهٔ Neon Auth منتقل نمی‌شود. پروژه از NextAuth و public.User استفاده می‌کند.
5. ترجیحاً مقصد خالی جدید بسازید و بکاپ تازه را با ON_ERROR_STOP و single-transaction بازیابی کنید. روی دیتابیس پر فایل قبلی را مجدداً اجرا نکنید. حذف/بازسازی مقصد قبلی نیازمند تصمیم صریح است.
6. همهٔ جدول‌ها، محتوای رکوردها، مجموع مبالغ، constraints، indexها، sequence شماره سفارش و سابقهٔ migrationها را تطبیق دهید؛ سپس بررسی فقط‌خواندنی Prisma را اجرا کنید.
7. روی هاست DATABASE_URL و DIRECT_URL هر دو به مقصد نهایی در `127.0.0.1:5432` اشاره کنند (نه پورت تونل ویندوز). تنها برای اتصال loopback می‌توان sslmode=disable گذاشت. دیگر secrets مثل AUTH_SECRET و OTP_SECRET تغییر نکنند.
8. متغیرهای cPanel و فایل‌های دارای اولویت بالاتر مثل .env.local نباید اتصال قدیمی را override کنند. از فایل env قبلی نسخهٔ امن با دسترسی 600 نگه دارید.
9. برنامه را build و پردازش واقعی LiteSpeed/Passenger را restart کنید؛ قبلاً دکمهٔ Restart به‌تنهایی کافی نبوده است. PID و زمان شروع پردازش را بررسی کنید؛ از PID قدیمی یا kill عمومی استفاده نکنید.
10. ورود، نمایش کاتالوگ، تاریخچهٔ سفارش و دسترسی مدیر را بررسی کنید. سپس نوشتن و jobهای دوره‌ای را فقط روی مقصد جدید فعال کنید. زمانبندی reconciliation باید به همین env نهایی وصل باشد.

پس از شروع نوشتن روی مقصد، برگشت سادهٔ URL به Neon داده‌های جدید را جا می‌گذارد؛ rollback نیازمند توقف نوشتن و تطبیق تغییرات است. Neon و بکاپ‌ها را تا تأیید نهایی حذف نکنید. بکاپ دوره‌ای خارج از همین هاست هم لازم است.

آزمون‌های نوشتنی همچنان فقط با TEST_DATABASE_URL و TEST_DIRECT_URL مجازند؛ دیتابیس منتقل‌شده جای دیتابیس آزمایش نیست.
